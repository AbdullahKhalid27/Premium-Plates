# Technical requirements
Phase 2 → 3. Extend the existing Next.js/TypeScript App Router and Tailwind project. Keep the GitHub Pages demo as the design reference and deploy the commerce application with a server runtime. Public catalogue HTML is crawlable. Prices and release rules run on the server.
Use PostgreSQL and Drizzle for transactional records, private S3-compatible storage for evidence, and a worker for malware screening and event delivery. Stripe hosted Checkout handles payment. Verify webhook signatures over the raw body and deduplicate event IDs. Use staff MFA, least-privilege roles and session expiry. Customer resume tokens must be random, hashed at rest, scoped to an order and time-limited.
A separate ClamAV scanning worker can move safe objects from quarantine to a private review area. Scanner outage leaves files pending. A Postgres-backed job runner such as pg-boss can deliver committed outbox events with retries. Keep provider-specific email and storage code behind small adapters. Redact documents, tokens, registrations and contact data from telemetry.
Hosting decision: evaluate the suggested Coolify/Hetzner deployment against who will patch it, monitor disk and scanner health, and restore it. Record the owner, recurring costs, recovery target and a successful offsite restore before production. These vendor choices are proposals.
First vertical slice: one approved SKU → test-mode Stripe payment → synthetic upload → staff approval → dispatch. Exercise duplicate webhooks, amount mismatch, scanner failure, expired links, cross-order access, MFA and refund reconciliation. Use an isolated scanner test fixture. Confirm backup recovery and retention jobs. Use synthetic data in staging.
Before live sales confirm the business’s original-document procedure, privacy notice, data responsibilities, applicable fee and impact assessment requirements, deletion periods and consumer terms with appropriate advisers. Keep the sale register retrievable for inspection. [DVLA record guidance](https://www.gov.uk/government/publications/inf1952-information-to-be-kept-by-registered-number-plate-suppliers). ## Phase orchestration and shared rules
F1–F5 build the customer frontend, B1 implements backend and staff review, F6 connects and releases commerce, A1 adds automations. Apply Research → Code → Push to each, with exact skills in Phase Prompts.md. GitHub delivery uses feature branches and reviewable PRs; server-hosting choice remains a documented deployment decision before taking payments.
Use one typed configuration shape across preview, quote and order, with independent vehicle/layout/side/size/base/finish/border/badge/slogan fields. Server-authoritative quoting and validation repeats every critical check. Frontend fixtures implement the same contracts.
Central guidance records contain stable rule ID, applicability, source URL/section, reviewed date, plain-language reason, correction and approval/version. The builder and future assistant consume the same approved records. The order preserves the evaluated rule version. Mechanical validation is deterministic. Staff approval and original-document procedure remain separately recorded.
DVLA VES provides vehicle details by registration; its documented response does not establish customer entitlement or certify the manufactured plate. Distinguish unavailable service, vehicle not found, formatting feedback and product-rule results. Preserve staff review for uncertain cases.
Use codebase-design/domain-modeling for interfaces, Ponytail for reuse, code-review and targeted tdd for transitions, Impeccable/Unslop for staff UI, pr for GitHub delivery.
